# Gameplay Contracts

## Design boundary

Hard constraints protect consistent rules. Soft risks preserve player choice. Objectives define success, and diagnostics explain decisions. Adding restrictions is not a substitute for believable simulation or interesting play.

This implementation is a lightweight game model, not a validated model of real equipment performance. Existing catalog names and descriptions do not establish the accuracy of their parameters.

## Authority and information

- `playerSide` defines command authority; `activePerspective` is only an observation view. `playMode: sandbox` explicitly grants editor authority. GOD view alone does not grant commands.
- Unit, mission, hangar and loadout actions enforce command authority in the store, not only in buttons. Spawning requires sandbox mode. Runtime loadout changes remain an editor feature.
- Ordinary enemy selection resolves to a contact owned by the player's side. Detection logs contain `contactId`, not a selectable hostile runtime unit. Enemy command logs and exact damage reports are withheld until debrief; own-platform losses remain available.
- Observed enemy missiles use the same radar observation model as interception. Revealing a missile does not reveal its historical trajectory back to launch.
- This is a local single-player sandbox. The client holds world truth; these boundaries prevent gameplay/UI leaks, not inspection through developer tools or a hostile network client.

## Fire control

`evaluateFireControl` returns `executable`, `risky` or `blocked`, with shared reasons for the engine and UI.

Hard constraints include authority (checked at the command boundary), platform capability, ammunition, mount cooldown, weapon/target compatibility, range to the observed aimpoint, and mandatory guidance support. It does not consult the hidden target's current position or HP to authorize an attack.

Stale information, large uncertainty and missing optional updates are risks. HOLD means no automatic fire, not an absolute prohibition on manual authorization. Risk authorization applies to one order, retains the standing doctrine and rechecks hard constraints at execution. Automatic offensive fire is conservative and declines risky solutions; per-unit/mission WRA further limits automatic fire by maximum range fraction, minimum retained rounds, allowed target domains and minimum observed threat level. Automatic missile defense evaluates every ready interceptor mount, discards non-executable solutions, applies the same WRA automatic range fraction/target-domain/minimum-threat filters, uses `salvoSize` as the desired total interceptors, respects retained inventory and subtracts existing in-flight interceptors, then chooses the executable weapon with the smallest positive range margin using stable inventory/ID tie-breaks. These WRA preferences never relax manual fire-control hard constraints. Mission doctrine overrides apply to fire/pursuit policy; sensor EMCON is controlled on the runtime unit.

An undiscovered runtime ID is not a blind-fire aimpoint. Ordinary weapons fire at retained contacts, not arbitrary coordinates. The bounded exception is a passive anti-radiation weapon launched at a recorded ESM bearing corridor/AOU; the in-flight weapon stores that observed geometry rather than a hidden runtime unit ID. A mandatory-support profile cannot be bypassed with risk confirmation.

## Guidance and collision

- Midcourse steering uses contact estimates delivered by an active observation source and, when shared across platforms, a compatible receiving datalink.
- Lost updates preserve the last estimate and extrapolate its recorded heading/speed. They never read hidden target motion for steering.
- Seeker activation distance, detection distance, full field-of-view angle and search timeout are separate configurable values in `WeaponSpec.guidanceProfile`.
- Search can continue after an initial failure. Acquisition and continued lock require the seeker's own current range/FOV/domain conditions. Semi-active guidance also requires configured support. Air-dropped lightweight torpedoes use a distinct launch envelope and airborne delivery phase, then switch at the recorded aimpoint to underwater speed/depth and bounded acoustic search; heavy direct-launch torpedoes are blocked on aircraft, and air-drop weapons are blocked on non-air platforms. A single ESM station creates a bearing corridor from its observed line of bearing; independent stations geometrically fuse into an ellipse. Passive anti-radiation weapons may fly to that recorded geometry but can physically acquire only a currently detectable emitter, including one that re-radiates during the search window. They are not globally omniscient.
- World truth is read only inside seeker observation and physical collision/damage resolution. Interceptors use the same guidance boundary as offensive weapons.
- Swept-path closest approach replaces coarse proximity thresholds. The application uses 0.25-second substeps; fixing the step establishes repeatability, not proven physical accuracy.

Default seeker parameters are deliberately provisional game values, differentiated by broad guidance family. They are overrideable and validated, but do not claim empirical calibration. Missiles apply a simplified speed decay curve beyond 55% of maximum range (`computeMissileEnergyFactor`, defining the No-Escape Zone `NEZ` preview and `TOF` estimate in `evaluateFireControl`), and non-semi-active terminal seekers can reacquire an alternative valid target within their FOV/range when the primary track is lost or destroyed. Simplified polygon-elevation ray checks (`hasRadarLineOfSight`, including valley re-entry across concave ridges) occlude low-altitude radar, ESM, IRST and non-acoustic seekers behind configured ridges; land-attack cruise missiles (`lacm`) climb 60m AGL over elevated polygons via simplified terrain-following, while low-altitude non-LACM weapons below an intervening ridge impact the terrain. Finite chaff, flare and acoustic-decoy inventories provide a simplified PRNG-driven terminal soft-kill chance against matching guidance families; these expendable effects do not create targetable entities. Separately, carried MALD/recon-UAV inventory and amphibious embarked `ground_force` inventory (within 18 km of valid land coastline) deploy full runtime units via `deployCarriedPlatform` or `DEPLOY_CARRIED` scenario events. High-resolution DEM propagation/diffraction and 6-DOF aerodynamic missile energy models remain out of scope.

## Resources, missions and damage

- Aircraft fuel is a cruise-time budget with a speed-dependent burn multiplier. Return reserve is estimated travel time to an available compatible carrier/base or a declared departure point, plus a safety margin. Carrier-launched aircraft cannot return to a fictitious destroyed host. Same-side non-tanker aircraft may queue at an active tanker with finite transferable fuel; rendezvous requires ≤1.5 km, ≤300 m altitude and ≤60 kt speed separation. Transfer conserves receiver fuel plus tanker offload inventory, one receiver is serviced at a time, and tanker/receiver return or loss deterministically interrupts and restores the receiver's prior route.
- Support aircraft do not withdraw simply because they have no weapons. Assigned attack/patrol aircraft withdraw when their task-relevant weapon set is depleted.
- Recovered carrier sorties leave active movement, sensors, fire and task rosters without being counted as losses, then enter their compatible host slot's deterministic turnaround queue. Each slot has a finite number of abstract refuel/rearm supply batches; completing turnaround consumes one batch and returns one airframe to ready inventory. A destroyed host loses onboard ready/reserve/queued inventory, while airborne sorties must divert to another active compatible host or eventually exhaust fuel.
- Mission AI uses observed contacts of the relevant domain, patrol-area/maximum-pursuit boundaries and a five-second decision interval. Players may create or edit missions from three or more same-side reference points; polygons are copied into the recorded command and degenerate, self-intersecting, mixed-side or unauthorized areas are rejected. Escort missions follow a declared same-side protected unit and react only to observed nearby threats; SEAD only prosecutes contacts with an observed emitter; AEW and tanker-support missions loop their declared route. Mission phases (`ingress`, `on_station`, `engaging`, `egress`, `recovering`) are deterministic. Manually assigned navigation takes priority. This is not an optimal tactical planner.
- Scenario coordinate waypoints are normalized at compile time into route legs with optional speed and altitude/depth. Runtime code uses only route legs. Formation commands preserve mission assignment while followers synchronize to a leader-relative offset; return/recovery overrides formation, and loss of the leader restores mission or manual navigation.
- OPFOR reactions are explicit scenario actions, not a hidden planner. `UNIT_DETECTED` triggers may require a minimum observed classification (`unknown`/`classified`/`identified`) and observed domain; category filters only match `identifiedCategory`, never hidden platform truth. Events can consume real hangar inventory to launch a sortie, reassign same-side units/groups, toggle EMCON, and schedule a coordinated release against a fresh observed contact. A sortie blocked by deck cooldown or temporarily unavailable ready inventory enters a deterministic retry queue; permanent inventory/host/loadout failures are retained with an explicit reason, while delayed orders launch no earlier than their declared simulation time. Coordinated orders store an opaque contact ID and release Tick; they are cancelled if that contact is no longer current and never select targets from hidden world truth.
- `autoEvade` reacts only to a side-observed, geometrically closing weapon track. It stores and later restores the interrupted route/mission/formation state, executes a deterministic Beam maneuver, and may consume finite countermeasures subject to cooldown. Lost observation is remembered for ten simulated seconds; return/recovery overrides evasion.
- Optional scenario-owned environment polygons, never online map tiles, define simplified land exclusion and acoustic zones. Surface/subsurface routes cannot cross land; configured land units must remain on land. Movement rechecks swept segments. Acoustic zones apply explicit shallow/deep sonar range factors; absence of environment data preserves the previous open-water behavior.
- Sandbox Scenario Builder changes are recorded commands over runtime groups, units, missions, objectives, events, reference points and environment. It can reposition units, reassign/edit groups, add objectives and create reference-point area triggers. Export uses these runtime definitions, strips event-runner progress and recovered historical sorties, then must pass the same `compileScenario` boundary before reimport.
- Carried MALD and reconnaissance-UAV counts are finite per launcher. Deployment creates an independent, observable runtime unit and decrements that inventory. Before positive identification, air contacts receive only broad observed-domain threat assumptions; close identification may reveal a decoy and reduce its threat value. Automatic defense therefore can spend ammunition on a plausible unresolved decoy without reading its hidden platform category.
- Coarse domain-specific damage profiles reduce speed, radar capability and reload performance. Mission-killed platforms cannot launch weapons, but an aircraft that safely withdrew is not a mission kill.
- Damage credit has a per-victim ceiling. Mission-kill credit and subsequent destruction share that ledger; key-target bonuses and objective rewards are not repeatedly granted each tick.

## Built-in content contract

Catalog `2026.12-CONTENT-EXPANSION-1` contains 44 platforms, 31 weapons, 24 sensors and 30 loadouts. The validator rejects dangling four-layer references and incompatible inventory before Tick 0. J-15T/F/A-18E/F/运-9G/B-1B/F-35B, 054B/Constellation, 039C/Taigei, 075/America and Z-20F/MH-60R form the principal maritime expansion packages; the catalog also includes the land and airbase units used by the joint-amphibious and inland air-land scenarios. HQ-16FE/ESSM Block 2 and HQ-10/RAM supplement the long-range layer, AIM-174B supplies finite ultra-long-range air defense, and Yu-11/Mk-54 use the dedicated airborne torpedo path.

The seven built-ins are the interactive command tutorial, East Sea Thunder, Deep Sea Carrier Hunt, Bashi Channel Blockade, Joint Amphibious Assault, Inland Mountain Strike and the short limited-information exercise. Fixed-seed no-command summaries for every built-in are generated by `bun run smoke:scenarios`; they prove deterministic finite closure, not human competitive balance.

## Objectives and debrief

Objectives support destruction, capability disablement, observation, preservation, withdrawal and area control (`control_area`). Area-control objectives evaluate active non-mission-killed combat strength inside the configured polygon: optional `holdDurationSec` tracks continuous hold progress (`1.0x` uncontested, `0.5x` under `>=2.5x` force-ratio suppression, paused when evenly contested, `-0.5x` decay when vacant/overwhelmed) for early completion, while omitting `holdDurationSec` requires holding uncontested or `>=2.5x` suppressing control at scenario timeout. A withdraw objective may define a versioned area and allowed domains; only explicitly listed same-side units that enter that area are marked recovered/withdrawn, and all listed units must complete before the objective succeeds. Air recovery outside a configured withdrawal area does not satisfy it. Preservation may require either survival or retained combat capability. Primary objectives decide mission success; optional objectives add score. Successful primary objectives with own losses produce a costly-victory assessment rather than an unconditional failure. The five-stage Westpac campaign carries forward readiness, capital-platform battle damage debt, carrier/airbase airframe attrition and 50% unreplenished scarce standoff munition expenditure across stages.

Only explicitly critical preservation failures end play early. If one side alone suffers such a failure, that side loses and the non-failing opponent receives victory/costly-victory according to its losses even when a time-gated required objective is still pending; simultaneous critical failures defeat both. Otherwise the scenario ends at its declared time limit, freezes simulation and exposes the objective ledger and combat report for review. A compact AAR ledger, independent of the 250-row visible log dock, records weapon events and fixed five-second truth-track samples. Complete opposing-force tracks and aggregate weapon/loss statistics are visible only after battle end or in explicit sandbox mode. The map ruler is display-only. Selected-contact threat circles use only observed domain, threat level and identified category assumptions; the estimator cannot accept a runtime unit or catalog lookup. The six-unit, fifteen-minute fictional exercise is a vertical slice, not a claim that difficulty or competing strategies have finished playtesting.

## Determinism and recordings

- The application accumulates measured elapsed time multiplied by playback speed. Only fixed 0.25-second ticks advance the model; delayed frames do not enlarge or skip ticks.
- The world stores PRNG state. Commands carry tick and sequence numbers; simulation entity IDs use those counters rather than wall time. Camera timestamps are presentation-only.
- A batch stops on the exact auto-pause/end tick. Unused wall-time budget is discarded on interruption, not replayed after the player resumes.
- `canonicalBattleState` excludes display state, wall-clock timestamps and fractional frame budgets. Identical initial state, rule/catalog version, environment, seed and tick-stamped commands must produce equal canonical states at the same tick.
- `captureBattleRecording` and `replayBattleRecording` back the JSON UI. Recording v2 stores and validates explicit ruleset, catalog and scenario-schema versions before changing the current battle; legacy v1 and version mismatches are rejected rather than silently replayed under different rules. Replay validates the action sequence, uses atomic ticks, and rolls back if a recorded action is no longer legal. Periodic canonical keyframe snapshots (`SNAPSHOT_INTERVAL_TICKS`) accelerate timeline scrubbing to arbitrary legal Ticks without recording the scrubber gesture as a command. Playback is bounded to 200,000 ticks / 10,000 commands.
- `captureBattleSave` and `restoreBattleSave` provide a resumable full-state save format (`BattleSaveState`) protected by a canonical digest and version checks, backing both browser `localStorage` autosave checkpoints (`1x/5x` main-thread and `15x/60x` Web Worker batches) and named multi-slot saves (`saveBattleToSlot` / `loadBattleFromSlot`, up to 8 slots plus `.save.json` file export).

## Verification

Run `bun test`, `bun run validate:db`, `bun run smoke:scenarios` and `bun run build`. Final gates additionally run `bun run test:e2e`, `bun run test:coverage`, `bun run docs:api` and `git diff --check`.

The gameplay regression suite covers command/view separation, Recording v2 compatibility and arbitrary-Tick replay, objective outcomes, Turnaround and finite inventories, RP missions, WRA, route legs, formations, OPFOR reactions, observed autoEvade, PRNG soft kill, environment boundaries, acoustic zones, Bearing-only fusion, area ARM reacquisition, AAR truth gating, refueling conservation, deployable deception/re-identification, Scenario Builder round-trips, fixed-step pause boundaries, rollback and finite scenario completion.
